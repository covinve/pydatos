"Esto es más rápido" sin medición es una opinión. Antes de optimizar, **mide**; después de optimizar, **vuelve a medir**.

## Medir el tiempo

```pyrun
import time

import numpy as np


def medir(funcion, *args, repeticiones=5):
    tiempos = []
    for _ in range(repeticiones):
        inicio = time.perf_counter()
        funcion(*args)
        tiempos.append(time.perf_counter() - inicio)
    return min(tiempos)      # el mínimo es el más estable: el resto es "ruido" del sistema


datos = np.random.default_rng(1).integers(0, 3600, 1_000_000)
print(f"Python: {medir(lambda d: sum((x + 59) // 60 for x in d.tolist()), datos) * 1000:.1f} ms")
print(f"NumPy:  {medir(lambda d: ((d + 59) // 60).sum(), datos) * 1000:.1f} ms")
```

:::consejo Reglas para medir bien
- Usa `time.perf_counter()` (no `time.time()`).
- Repite varias veces y quédate con el mínimo o la mediana.
- La primera ejecución suele ser más lenta (cachés, carga de librerías): descártala o repite.
- Mide con datos de tamaño realista: una optimización que gana con 1.000 filas puede perder con 10 millones.
:::

## Medir la memoria

`tracemalloc` (módulo 11) mide la memoria que reserva Python, pero **no** la que usan internamente Polars, DuckDB o NumPy en código nativo. Para medir el proceso completo usa `psutil` (lo tienes instalado):

```python
import os

import psutil


def memoria_mb() -> float:
    return psutil.Process(os.getpid()).memory_info().rss / 1e6
```

Para el **pico** de un proceso completo, lo más simple es ejecutarlo en un subproceso y mirar su consumo máximo, o observar el Administrador de tareas mientras corre.

## Paralelizar trabajo independiente

Si tienes 30 archivos diarios y cada uno se procesa por separado, puedes procesar varios **a la vez**, uno por núcleo del procesador:

```python
from concurrent.futures import ProcessPoolExecutor
from pathlib import Path


def resumir_archivo(ruta: Path) -> dict:
    ...  # procesa UN archivo y devuelve un resumen pequeño


if __name__ == "__main__":
    archivos = sorted(Path("datos/diarios").glob("cdr_*.csv"))
    with ProcessPoolExecutor() as ejecutor:          # un proceso por núcleo, por defecto
        resumenes = list(ejecutor.map(resumir_archivo, archivos))
    total = combinar(resumenes)
```

| | `ThreadPoolExecutor` (hilos) | `ProcessPoolExecutor` (procesos) |
|---|---|---|
| Ideal para | Esperar: descargas, APIs, bases de datos | Calcular: CPU al 100 % |
| Comparten memoria | Sí | No: cada proceso tiene la suya |
| Costo de arranque | Bajo | Mayor (cada proceso inicia Python) |
| En Python puro de cálculo | No acelera (el GIL) | Sí acelera |

:::error El guardián es obligatorio
En Windows, `ProcessPoolExecutor` **requiere** que el código que lo usa esté dentro de `if __name__ == "__main__":`. Cada proceso hijo importa tu script; sin el guardián, cada hijo intentaría crear más procesos.
:::

:::capo Los motores ya son paralelos
DuckDB y Polars ya usan todos los núcleos dentro de una sola consulta. Paralelizar "por fuera" sirve sobre todo para Python puro o Pandas, o cuando cada archivo requiere lógica muy distinta.
:::

## Elegir con datos

Una tabla de mediciones como esta (tus números van a variar) es la mejor forma de decidir:

| Validar 1 GB (14 M de registros) | Tiempo | Memoria máxima |
|---|---|---|
| Python puro (módulo 11) | ~60 s | ~20 MB |
| Pandas completo (módulo 13) | ~25 s | ~4 GB |
| Pandas por bloques (módulo 14) | ~30 s | ~400 MB |
| Polars perezoso | ~4 s | ~1 GB |
| DuckDB | ~3 s | ~500 MB |

Con 20 GB, multiplica los tiempos por 20… y descarta lo que no cabe en memoria.

:::telco La herramienta según el día
En el trabajo diario lo práctico es: DuckDB o Polars para lo pesado (validar, agregar, cruzar los archivos grandes), y Pandas para el resultado ya resumido (que tiene miles de filas, no millones), donde su ecosistema de gráficos y análisis es imbatible.
:::
