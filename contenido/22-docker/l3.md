Un contenedor es desechable: lo que escribe dentro desaparece al borrarlo. Los datos de entrada (los 20 GB) y los resultados viven **fuera**, y se conectan al contenedor con **volúmenes**.

## Dos tipos de volumen

| Tipo | Sintaxis | Ideal para |
|---|---|---|
| **Montaje de carpeta** (*bind mount*) | `-v D:\datos\cdr:/datos:ro` | Tus archivos: CDR de entrada, carpeta de salidas |
| **Volumen con nombre** | `-v pgdata:/var/lib/postgresql/data` | Datos que maneja el contenedor (la base de PostgreSQL) |

```powershell
docker run --rm `
  -v D:\datos\20GB:/datos:ro `
  -v ${PWD}\salidas:/salidas `
  -e TELCO_PERIODO=202609 `
  -e TELCO_MEMORIA_DUCKDB=8GB `
  --memory 10g `
  telco-pipeline:1.0 validar /datos --salida /salidas
```

- `:ro` monta en **solo lectura**: el contenedor no puede modificar tus datos originales por error.
- Dentro del contenedor, las rutas son de Linux: `/datos`, no `D:\datos`. Tu código debe recibir las rutas por configuración (módulo 21), nunca tenerlas escritas.

:::consejo Rendimiento con Docker Desktop en Windows
Docker Desktop corre sobre **WSL2** (Linux). Leer archivos montados desde `D:\` atraviesa una capa de traducción y puede ser **varias veces más lento** que dentro de Linux. Para los 20 GB, copia los datos una vez al sistema de archivos de WSL (`\\wsl$\Ubuntu\home\tu_usuario\datos`) o a un volumen con nombre, y monta desde ahí. Para archivos pequeños, la diferencia no se nota.
:::

## Memoria y CPU

Docker Desktop limita la memoria total de los contenedores (por defecto, la mitad de la RAM). En tu computador de 16 GB:

- `--memory 10g` limita un contenedor a 10 GB: si se pasa, se detiene (el famoso código de salida **137**, "OOM killed").
- Combínalo con `SET memory_limit` de DuckDB por debajo de ese límite (por ejemplo 8 GB): DuckDB usará disco en lugar de pasarse.
- La memoria total para WSL se ajusta en `%USERPROFILE%\.wslconfig` (`[wsl2]` → `memory=12GB`).

## Configuración y secretos

```powershell
docker run --rm --env-file .env telco-pipeline:1.0 mostrar
```

`--env-file` pasa todas las variables de tu `.env` **al ejecutar**: la imagen no contiene secretos, y la misma imagen sirve para pruebas y producción cambiando solo el archivo.

## Puertos y red

Un contenedor tiene su propia red. Para acceder desde tu Windows a un servicio dentro del contenedor:

```powershell
docker run -d --name bd -p 5433:5432 -e POSTGRES_PASSWORD=x postgres:16
```

`-p 5433:5432` = el puerto **5433 de tu máquina** va al **5432 del contenedor**. Desde Python en Windows te conectas a `localhost:5433`.

Entre contenedores (lección 4) no se usa `localhost`: cada contenedor se llama por su **nombre de servicio** (`bd:5432`).

:::error localhost no es lo que crees
Dentro de un contenedor, `localhost` es **el propio contenedor**. Si tu aplicación en Docker intenta conectarse a `localhost:5432` buscando el PostgreSQL de otro contenedor (o de tu Windows), no lo encontrará. Usa el nombre del servicio, o `host.docker.internal` para llegar a tu Windows.
:::
