En el módulo 19 aislaste dependencias con **dobles en memoria** escritos a mano. `unittest.mock` crea dobles **automáticos** que, además, registran cómo se los llamó. Son ideales cuando quieres verificar una **interacción** ("¿se envió exactamente un correo con este asunto?") o reemplazar algo que no inyectaste.

## Mock: un objeto que acepta todo

```pyrun
from unittest.mock import Mock

notificador = Mock()
notificador.enviar("ALERTA", "7 % rechazados")         # cualquier método existe
notificador.enviar("ALERTA", "9 % rechazados")

print(notificador.enviar.call_count)                     # 2
print(notificador.enviar.call_args)                      # la última llamada
print(notificador.enviar.call_args_list)
notificador.enviar.assert_called_with("ALERTA", "9 % rechazados")

api = Mock()
api.tarifa.return_value = {"plan_id": "HOG30", "tarifa_minuto": 120}   # qué devuelve
print(api.tarifa("HOG30"))

api.consumos.side_effect = [ConnectionError("caída"), [{"linea": "3001"}]]   # una excepción y luego un valor
for _ in range(2):
    try:
        print(api.consumos("202609"))
    except ConnectionError as e:
        print("falló:", e)
```

| Atributo / método | Para qué |
|---|---|
| `m.return_value = x` | Lo que devuelve al llamarlo |
| `m.side_effect = Excepcion(...)` | Lanza esa excepción |
| `m.side_effect = [a, b, c]` | Devuelve (o lanza) uno por llamada, en orden |
| `m.side_effect = funcion` | Calcula la respuesta con tu función |
| `m.assert_called_once_with(...)` | Falla si no se llamó exactamente una vez con esos argumentos |
| `m.assert_not_called()` | Falla si se llamó |
| `m.call_args_list` | Todas las llamadas, para revisarlas a mano |

:::error El peligro del Mock que acepta todo
`notificador.enviarr(...)` (con un error de tipeo) **no falla**: un `Mock` acepta cualquier método. Usa `Mock(spec=NotificadorArchivo)` o `create_autospec(NotificadorArchivo)` para que solo acepte los métodos (y argumentos) que existen de verdad.
:::

## patch: reemplazar lo que no inyectaste

A veces el código usa algo directamente (`requests.get`, `time.sleep`, `datetime.now`) y no puedes o no quieres cambiar su diseño. `patch` lo reemplaza **temporalmente** durante la prueba:

```python
# descarga.py
import requests

def tarifa(plan_id):
    r = requests.get(f"https://api.telco.example/tarifas/{plan_id}", timeout=10)
    r.raise_for_status()
    return r.json()

# test_descarga.py
from unittest.mock import patch
import descarga

def test_tarifa():
    with patch("descarga.requests.get") as get:            # se reemplaza DONDE SE USA
        get.return_value.json.return_value = {"tarifa_minuto": 120}
        assert descarga.tarifa("HOG30") == {"tarifa_minuto": 120}
        get.assert_called_once_with("https://api.telco.example/tarifas/HOG30", timeout=10)
```

:::consejo Parchea donde se usa, no donde se define
Si `informe.py` hace `from datetime import datetime`, el nombre que usa es `informe.datetime`: hay que parchear `"informe.datetime"`, no `"datetime.datetime"`. Es el error más común con `patch`.
:::

## monkeypatch de pytest

Para variables de entorno, atributos y el directorio actual, el *fixture* `monkeypatch` es más simple y deshace todo al terminar la prueba:

```python
def test_token_desde_entorno(monkeypatch):
    monkeypatch.setenv("TELCO_API_TOKEN", "abc")
    monkeypatch.delenv("HTTPS_PROXY", raising=False)
    assert leer_token() == "abc"

def test_sin_esperas(monkeypatch):
    esperas = []
    monkeypatch.setattr("cliente.time.sleep", esperas.append)
    ...

def test_relativo(monkeypatch, tmp_path):
    monkeypatch.chdir(tmp_path)          # el directorio actual es una carpeta temporal
```

## ¿Mock o doble en memoria?

| Situación | Mejor opción |
|---|---|
| Verificar **que** se llamó algo y **cómo** (un envío, un reintento) | `Mock` |
| Simular errores en un orden preciso (falla, falla, funciona) | `Mock` con `side_effect` |
| Reemplazar algo que no inyectaste (`requests.get`, `time.sleep`) | `patch` / `monkeypatch` |
| Un repositorio con datos que el caso de uso consulta varias veces | Doble en memoria (`ClientesEnMemoria`) |
| Muchas pruebas sobre la misma dependencia | Doble en memoria: las pruebas quedan más legibles |

:::capo Demasiados mocks
Si una prueba necesita parchear cinco cosas, el código probablemente está muy acoplado: es una señal de diseño, no un problema de las pruebas. Y una prueba que verifica cada llamada interna se rompe con cualquier refactorización aunque el resultado siga siendo correcto. Verifica **resultados** siempre que puedas, e **interacciones** solo cuando la interacción **es** el resultado (como enviar una alerta).
:::

## Cuestionario

? ¿Qué hace `m.side_effect = [ValueError(), 5]`?
- [ ] Siempre lanza ValueError
- [x] La primera llamada lanza ValueError y la segunda devuelve 5
- [ ] Devuelve la lista
- [ ] Nada: side_effect solo acepta funciones
> Con una lista, cada llamada toma el siguiente elemento: si es una excepción, la lanza.

? `informe.py` hace `from datetime import datetime`. ¿Qué parcheas?
- [ ] `"datetime.datetime"`
- [x] `"informe.datetime"`
- [ ] `"datetime"`
- [ ] No se puede parchear
> Se parchea el nombre en el módulo donde se usa.

? Llamas por error `mock.enviarr(...)` en el código. ¿Qué pasa con un `Mock()` normal?
- [ ] AttributeError
- [x] Nada: el Mock acepta cualquier método, por eso conviene `spec=` o `create_autospec`
- [ ] La prueba falla siempre
- [ ] Python corrige el nombre
> Sin `spec`, el Mock no conoce la interfaz real y acepta errores de tipeo.
