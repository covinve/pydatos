Las pruebas unitarias verifican piezas aisladas con dobles. Pero ¿el adaptador SQLite funciona de verdad con SQLite? ¿La CLI lee bien el CSV en latin-1? Eso lo responden las **pruebas de integración**: las piezas reales, juntas, con archivos y bases de verdad (temporales).

## conftest.py: fixtures compartidos

Los *fixtures* definidos en `tests/conftest.py` están disponibles en todas las pruebas de esa carpeta, sin importarlos:

```python
# tests/conftest.py
import shutil
import sqlite3
from pathlib import Path

import pytest

DATOS = Path(__file__).parent / "datos_prueba"


@pytest.fixture(scope="session")
def datos_prueba():
    """La carpeta con la muestra (solo lectura)."""
    return DATOS


@pytest.fixture
def carpeta_trabajo(tmp_path):
    """Una copia de los datos de prueba que cada prueba puede modificar."""
    destino = tmp_path / "datos"
    shutil.copytree(DATOS, destino)
    return destino


@pytest.fixture
def bd(tmp_path):
    con = sqlite3.connect(tmp_path / "prueba.db")
    yield con                      # lo que va después del yield es la limpieza
    con.close()
```

| `scope=` | El fixture se crea… |
|---|---|
| `"function"` (por defecto) | Una vez por prueba: aislamiento total |
| `"module"` | Una vez por archivo de pruebas |
| `"session"` | Una vez por toda la ejecución: para cosas caras y de solo lectura |

:::reto Un fixture que limpia
El módulo `repo.py` tiene `guardar(con, linea, plan_id)` y `contar_de_plan(con, plan_id)` sobre la tabla `clientes (linea, plan_id)`.

1. Escribe el fixture `bd`: crea una conexión SQLite en memoria con la tabla `clientes`, la entrega con `yield` y **la cierra** después.
2. Escribe al menos 2 pruebas que lo usen.

El curso corre tus pruebas contra el código correcto y contra una versión de `contar_de_plan` que cuenta **todos** los clientes, sin filtrar por plan.

```pyreto
@pytest.fixture

    ...


def test_cuenta_los_del_plan(bd):
    ...
```

:::pista
Dentro del fixture: `con = sqlite3.connect(":memory:")`, `con.execute("CREATE TABLE clientes (linea TEXT, plan_id TEXT)")`, `yield con` y, después, `con.close()`. En la prueba, guarda clientes de **dos** planes distintos y verifica `contar_de_plan(bd, "HOG30")`.
:::

```pyprueba
import ast

CORRECTA = (
    "def guardar(con, linea, plan_id):\n"
    "    con.execute('INSERT INTO clientes VALUES (?, ?)', (linea, plan_id))\n\n"
    "def contar_de_plan(con, plan_id):\n"
    "    return con.execute('SELECT COUNT(*) FROM clientes WHERE plan_id = ?', (plan_id,)).fetchone()[0]\n"
)


def correr(implementacion):
    return correr_pytest(codigo, {"repo": implementacion})


def prueba_fixture():
    """bd es un fixture con yield que cierra la conexión"""
    funcion = next((n for n in ast.walk(ast.parse(codigo)) if isinstance(n, ast.FunctionDef) and n.name == "bd"), None)
    assert funcion is not None and funcion.decorator_list, "Define el fixture bd con @pytest.fixture"
    assert any(isinstance(n, ast.Yield) for n in ast.walk(funcion)), "Entrega la conexión con yield"
    assert ".close()" in ast.unparse(funcion), "Cierra la conexión después del yield"


def prueba_pasan():
    """Tus pruebas pasan con el código correcto"""
    resultado, texto = correr(CORRECTA)
    assert resultado != 5, "pytest no encontró pruebas"
    assert resultado == 0, "Alguna prueba falla con el código CORRECTO:\n" + texto[-900:]


def prueba_atrapa_sin_filtro():
    """Atrapan el conteo sin filtrar por plan"""
    mutante = CORRECTA.replace(" WHERE plan_id = ?', (plan_id,))", "')")
    resultado, _ = correr(mutante)
    assert resultado == 1, "Ninguna prueba falló con el conteo sin filtro. Pista: guarda clientes de dos planes distintos"
```

## Marcadores

Las pruebas lentas no deberían correr en cada cambio:

```python
import pytest

@pytest.mark.lento
def test_carga_de_un_millon_de_filas(tmp_path):
    ...

@pytest.mark.skipif("TELCO_DB_URL" not in os.environ, reason="sin PostgreSQL")
def test_postgres():
    ...
```

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
markers = ["lento: pruebas que tardan más de unos segundos"]
addopts = "-m 'not lento'"          # por defecto, sin las lentas
```

`pytest -m lento` corre solo las lentas; `pytest -m ""` corre todas.

## Parametrizar en serio

```python
@pytest.mark.parametrize(
    ("segundos", "minutos"),
    [(0, 0), (1, 1), (59, 1), (60, 1), (61, 2), (3600, 60)],
    ids=["cero", "un-segundo", "casi-minuto", "minuto-exacto", "minuto-y-uno", "una-hora"],
)
def test_minutos_facturables(segundos, minutos):
    assert minutos_facturables(segundos) == minutos
```

Con `ids`, un fallo se lee `test_minutos_facturables[minuto-exacto]` en lugar de `[60-1]`.

:::reto Casos con nombre
El módulo `franjas.py` tiene `franja(hora)`: `"nocturna"` de 0 a 5, `"diurna"` de 6 a 17 y `"tarde"` de 18 a 23. Escribe **una** prueba parametrizada, con `ids` legibles, que cubra los **límites** de cada franja (al menos 6 casos).

El curso la corre contra la versión correcta y contra dos con errores en los límites: una con `<= 6` para la nocturna y otra con `< 17` para la diurna.

```pyreto
import pytest

from franjas import franja


# Tu prueba parametrizada con ids

```

:::pista
Los límites son 0, 5, 6, 17, 18 y 23. Por ejemplo: `@pytest.mark.parametrize(("hora", "esperada"), [(5, "nocturna"), (6, "diurna"), ...], ids=["fin-noche", "inicio-dia", ...])`.
:::

```pyprueba
import ast

CORRECTA = (
    "def franja(hora):\n"
    "    if hora <= 5:\n"
    "        return 'nocturna'\n"
    "    if hora <= 17:\n"
    "        return 'diurna'\n"
    "    return 'tarde'\n"
)


def correr(implementacion):
    return correr_pytest(codigo, {"franjas": implementacion})


def prueba_ids():
    """Usa parametrize con ids"""
    llamadas = [n for n in ast.walk(ast.parse(codigo)) if isinstance(n, ast.Call) and "parametrize" in ast.unparse(n.func)]
    assert llamadas, "Usa @pytest.mark.parametrize"
    assert any(k.arg == "ids" for c in llamadas for k in c.keywords), "Dale nombres a los casos con ids=[...]"


def prueba_pasan():
    """Tus casos pasan con el código correcto"""
    resultado, texto = correr(CORRECTA)
    assert resultado != 5, "pytest no encontró pruebas"
    assert resultado == 0, "Algún caso falla con el código CORRECTO:\n" + texto[-900:]
    casos = int(texto.split(" passed")[0].split()[-1]) if " passed" in texto else 0
    assert casos >= 6, f"Agrega al menos 6 casos; pytest ejecutó {casos}"


def prueba_atrapa_limites():
    """Atrapan los dos errores de límite"""
    for viejo, nuevo, pista in (("hora <= 5", "hora <= 6", "las 6"), ("hora <= 17", "hora < 17", "las 17")):
        resultado, _ = correr(CORRECTA.replace(viejo, nuevo))
        assert resultado == 1, f"Ningún caso falló con el error en {pista}: prueba ese límite exacto"
```

## Cobertura

`pytest-cov` mide qué líneas ejecutaron tus pruebas:

```powershell
pytest --cov=src/conciliacion --cov-report=term-missing
```

```text
Name                          Stmts   Miss  Cover   Missing
-----------------------------------------------------------
src/conciliacion/reglas.py       42      0   100%
src/conciliacion/lectura.py      38      6    84%   51-53, 77-79
src/conciliacion/cli.py          25     25     0%
-----------------------------------------------------------
TOTAL                           105     31    70%
```

`Missing` te dice qué líneas nunca se ejecutaron: casi siempre son los caminos de error (`except`, el `if` raro). Agrega `--cov-report=html` y abre `htmlcov/index.html` para verlas marcadas en rojo.

:::capo 100 % de cobertura no es 100 % correcto
La cobertura dice qué líneas **se ejecutaron**, no qué se **verificó**. Una prueba sin `assert` sube la cobertura sin probar nada. Úsala para encontrar lo **no probado**, no como meta. Un objetivo razonable: dominio cerca del 100 %, el resto por encima de 80 %. Las pruebas de mutantes del módulo 10 miden algo más honesto: si tus pruebas **detectan** errores.
:::

- [ ] En `__init__.py`
> pytest los encuentra automáticamente para todas las pruebas de esa carpeta y sus subcarpetas.

? Tu proyecto tiene 100 % de cobertura. ¿Qué significa?
- [ ] Que no tiene errores
- [x] Que todas las líneas se ejecutaron en alguna prueba, no necesariamente que se verificaron bien

- [ ] Que mypy no encuentra errores
> La cobertura mide ejecución, no la calidad de las verificaciones.
