Con lo que sabes, el archivo de 20 GB tiene dos caminos: Python puro línea por línea (memoria constante, pero lento) o Pandas por bloques (rápido, pero hay que programar a mano lo que cruza bloques, y medianas o percentiles no se pueden combinar). Existe un tercer camino que tiene lo mejor de ambos.

## Los límites de Pandas

| Límite | Consecuencia con 20 GB |
|---|---|
| Carga todo en memoria (y suele ocupar 2–5 veces el tamaño del archivo) | No cabe en 16 GB |
| Ejecuta cada operación inmediatamente | No puede optimizar el plan completo |
| Usa principalmente **un núcleo** del procesador | Tu CPU de 8 núcleos trabaja al 12 % |
| Cada paso crea DataFrames intermedios | Más memoria y más tiempo |

## Los motores columnares

**DuckDB** y **Polars** son motores modernos escritos en C++ y Rust que:

- **Leen solo las columnas necesarias** (y con Parquet, solo los bloques necesarios).
- **Procesan por lotes** (*streaming*): no necesitan el archivo completo en memoria.
- **Usan todos los núcleos** del procesador.
- **Optimizan la consulta completa** antes de ejecutarla: si filtras después de cruzar, mueven el filtro antes del cruce.
- **Usan el disco** cuando la memoria no alcanza (*out-of-core*).

:::pasos Ejecución inmediata vs. perezosa
:::paso Pandas: cada línea se ejecuta al instante
```python
df = pd.read_csv("cdr.csv")              # lee TODO (20 GB)
voz = df[df["tipo"] == "VOZ"]            # copia el 30 %
resumen = voz.groupby("linea")["dur"].sum()
```
Cada línea trabaja sobre el resultado completo de la anterior. Leer todo el archivo era innecesario: solo se usaron dos columnas y el 30 % de las filas.
:::
:::paso Perezoso: primero se describe, después se ejecuta
```python
plan = (pl.scan_csv("cdr.csv")           # no lee nada todavía
          .filter(pl.col("tipo") == "VOZ")
          .group_by("linea").agg(pl.col("dur").sum()))
resumen = plan.collect()                 # ahora sí
```
`scan_csv` solo describe la fuente. Al llamar `collect()`, el motor ve el plan completo: lee solo `tipo`, `linea` y `dur`, filtra mientras lee y agrupa en paralelo.
:::
:::

## Apache Arrow: el idioma común

**Arrow** es un formato estándar para tablas en memoria, por columnas. Pandas (con `pyarrow`), Polars y DuckDB lo entienden, así que pueden pasarse datos **sin copiarlos**. Por eso es barato combinarlos: consultar con DuckDB, seguir en Pandas, graficar con matplotlib.

```pyrun
import duckdb
import pandas as pd
import polars as pl
import pyarrow  # noqa: F401  (Arrow: el formato que comparten; Polars lo usa para convertir desde Pandas)

pdf = pd.DataFrame({"tipo": ["VOZ", "SMS", "VOZ"], "dur": [125, 0, 61]})
print(duckdb.sql("SELECT tipo, SUM(dur) AS total FROM pdf GROUP BY tipo ORDER BY tipo").df())   # DuckDB lee el DataFrame de Pandas
print(pl.from_pandas(pdf).group_by("tipo").agg(pl.col("dur").sum()).sort("tipo"))             # Polars desde Pandas
```

## ¿Cuál uso?

| Situación | Herramienta |
|---|---|
| Archivo que cabe cómodo en memoria, análisis interactivo | Pandas |
| Archivo grande, preguntas que se expresan bien en SQL | DuckDB |
| Archivo grande, transformaciones encadenadas en Python | Polars |
| Lógica muy particular registro por registro | Python puro (o Polars con expresiones) |
| Muchos archivos independientes | Cualquiera de los anteriores, en paralelo |

No son excluyentes: el mismo proceso puede leer con DuckDB, transformar con Polars y graficar desde Pandas.

:::telco 20 GB en tu computador de la casa
Con DuckDB, la validación completa del archivo de 20 GB (incluidos los duplicados exactos, que con Python puro necesitaban 15 GB de memoria) corre en pocos minutos en un computador de 16 GB. Lo harás en el ejercicio 7.
