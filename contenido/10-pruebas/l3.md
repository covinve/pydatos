Escribir pruebas es fácil. Escribir **buenas** pruebas, las que atrapan errores reales, requiere pensar qué casos elegir.

## Clases de equivalencia

Agrupa las entradas posibles en **clases** que el código trata igual, y prueba al menos un caso de cada una. Para `minutos_facturables(segundos)`:

| Clase | Ejemplo |
|---|---|
| Cero (no contestada) | 0 |
| Menos de un minuto | 1, 30, 59 |
| Minuto exacto | 60, 120 |
| Un poco más de un minuto | 61 |
| Llamada larga | 3600 |

## Casos borde: donde viven los errores

Los errores se esconden en los **límites**: el último valor que no se cobra y el primero que sí; la lista vacía; el plan ilimitado; la fecha de corte exacta.

| Regla | Casos borde |
|---|---|
| "El exceso se cobra por encima de lo incluido" | consumo = incluido, incluido + 1 |
| "Descuento a quien se dio de alta antes del 2023-09-01" | 2023-08-31 y 2023-09-01 exactos |
| "Franja nocturna de 22:00 a 05:59" | 21:59, 22:00, 05:59, 06:00 |
| Cualquier lista | vacía, un elemento, muchos |
| Ilimitado = -1 | -1, 0 |

:::consejo Pregunta "¿qué pasaría si…?"
¿Y si la lista está vacía? ¿Y si el número es negativo? ¿Y si el texto tiene espacios? ¿Y si la fecha es el 29 de febrero? Cada respuesta que te haga dudar es una prueba que vale la pena escribir.
:::

:::reto Pruebas en el límite
El módulo `promociones.py` tiene `aplica_descuento(fecha_alta)`: `True` para los clientes dados de alta **antes** del 1 de septiembre de 2023.

Escribe pruebas que atrapen estas tres versiones con errores:

- usa `<=` en lugar de `<`;
- compara contra el 31 de agosto en lugar del 1 de septiembre;
- devuelve siempre `True`.

```pyreto

from promociones import aplica_descuento


# Escribe tus pruebas en los casos borde

```

:::pista
Los errores viven en el límite: prueba el 31 de agosto de 2023 (sí aplica) y el 1 de septiembre de 2023 (no aplica). Una fecha muy posterior atrapa al que siempre dice `True`.
:::

```pyprueba
CORRECTA = "from datetime import date\n\ndef aplica_descuento(fecha_alta):\n    return fecha_alta < date(2023, 9, 1)\n"


def correr(implementacion):
    return correr_pytest(codigo, {"promociones": implementacion})


def prueba_pasan():
    """Tus pruebas pasan con el código correcto"""
    resultado, texto = correr(CORRECTA)
    assert resultado != 5, "pytest no encontró pruebas: los nombres deben empezar con test_"
    assert resultado == 0, "Alguna prueba falla con el código CORRECTO:\n" + texto[-900:]


def prueba_atrapa_menor_o_igual():
    """Atrapan el <= en lugar de <"""
    resultado, _ = correr(CORRECTA.replace("<", "<="))
    assert resultado == 1, "Ninguna prueba falló con <=. Pista: el 1 de septiembre exacto"


def prueba_atrapa_fecha_corrida():
    """Atrapan la comparación contra el 31 de agosto"""
    resultado, _ = correr(CORRECTA.replace("date(2023, 9, 1)", "date(2023, 8, 31)"))
    assert resultado == 1, "Ninguna prueba falló con la fecha corrida. Pista: el 31 de agosto exacto"


def prueba_atrapa_siempre_true():
    """Atrapan la versión que siempre dice True"""
    resultado, _ = correr("def aplica_descuento(fecha_alta):\n    return True\n")
    assert resultado == 1, "Ninguna prueba falló con la versión que siempre dice True"
```


## Pruebas de regresión

Cuando encuentras un error, **antes de arreglarlo** escribe una prueba que lo reproduzca (debe fallar). Luego arréglalo (la prueba pasa). Esa prueba queda para siempre: si alguien reintroduce el error, la prueba lo atrapa.

```python
def test_regresion_iva_de_150_redondea_hacia_arriba():
    """Ticket FAC-231: el IVA de $150 se calculaba como $28 en lugar de $29."""
    assert calcular_iva(150) == 29
```

:::reto La prueba del ticket
Llegó el ticket **FAC-318**: "a los clientes con plan ilimitado (`minutos_incluidos = -1`) se les cobró exceso de voz". El módulo `voz.py` ya está corregido.

Escribe una prueba de regresión, con un docstring que cite el ticket, que **falle** con la versión vieja (la que no revisaba el `-1`) y **pase** con la corregida. La función es `valor_voz(minutos, incluidos, tarifa)`.

```pyreto
from voz import valor_voz


# Escribe la prueba de regresión del ticket FAC-318

```

:::pista
Con la versión vieja, `valor_voz(500, -1, 120)` da `(500 - (-1)) * 120 = 60120`. La corregida da `0`. Escribe `def test_regresion_ilimitado_no_paga_exceso():` con un docstring que mencione `FAC-318` y `assert valor_voz(500, -1, 120) == 0`.
:::

```pyprueba
import ast

CORREGIDA = (
    "def valor_voz(minutos, incluidos, tarifa):\n"
    "    if incluidos == -1:\n"
    "        return 0\n"
    "    return max(0, minutos - incluidos) * tarifa\n"
)
VIEJA = "def valor_voz(minutos, incluidos, tarifa):\n    return max(0, minutos - incluidos) * tarifa\n"


def correr(implementacion):
    return correr_pytest(codigo, {"voz": implementacion})


def prueba_cita_ticket():
    """La prueba cita el ticket en su docstring"""
    pruebas = [n for n in ast.walk(ast.parse(codigo)) if isinstance(n, ast.FunctionDef) and n.name.startswith("test_")]
    assert pruebas, "Escribe una función test_..."
    assert any("FAC-318" in (ast.get_docstring(p) or "") for p in pruebas), "Cita el ticket FAC-318 en el docstring de la prueba"


def prueba_pasa_con_corregida():
    """Pasa con la versión corregida"""
    resultado, texto = correr(CORREGIDA)
    assert resultado == 0, "La prueba falla con la versión CORREGIDA:\n" + texto[-900:]


def prueba_falla_con_vieja():
    """Falla con la versión vieja (reproduce el error)"""
    resultado, _ = correr(VIEJA)
    assert resultado == 1, "Tu prueba no reproduce el error: debería fallar con la versión vieja"
```

```pypreparacion
from pathlib import Path

Path("voz.py").write_text(
    "def valor_voz(minutos, incluidos, tarifa):\n"
    "    if incluidos == -1:\n"
    "        return 0\n"
    "    return max(0, minutos - incluidos) * tarifa\n",
    encoding="utf-8",
)
```

```pysolucion

    """Ticket FAC-318: al plan ilimitado (-1) se le cobraba exceso de voz."""
    assert valor_voz(500, -1, 120) == 0
```

## El ciclo TDD: rojo, verde, refactorizar

En el **desarrollo guiado por pruebas** (*Test-Driven Development*) escribes la prueba **antes** que el código:

:::pasos El ciclo TDD
:::paso 🔴 Rojo: escribe una prueba que falle
```python
def test_valor_sms_cobra_exceso():
    assert valor_sms(120, incluidos=100, tarifa=60) == 1200
```
Todavía no existe `valor_sms`: la prueba falla. Eso confirma que la prueba sirve para algo.
:::
:::paso 🟢 Verde: el código mínimo para que pase
```python
def valor_sms(cantidad, incluidos, tarifa):
    return max(0, cantidad - incluidos) * tarifa
```
No te adelantes: escribe solo lo necesario para la prueba actual.
:::
:::paso 🔵 Refactoriza con red de seguridad
Con la prueba en verde, mejora el código (nombres, duplicación, estructura). Si algo se rompe, la prueba te avisa al instante.
:::
:::paso 🔁 Repite con el siguiente caso
```python
def test_valor_sms_ilimitado_no_cobra():
    assert valor_sms(2000, incluidos=-1, tarifa=0) == 0
```
Rojo de nuevo. Agregas el caso del ilimitado, verde, refactorizas… y así hasta cubrir la regla completa.
:::
:::

TDD no es obligatorio, pero practicarlo cambia la forma de pensar: te obliga a definir **qué** debe hacer el código antes de pensar **cómo**.

:::reto Rojo, verde
Estas pruebas ya están escritas y hoy están en rojo, porque `valor_sms` no existe:

```python
def test_cobra_el_exceso():
    assert valor_sms(120, incluidos=100, tarifa=60) == 1200

def test_sin_exceso_no_cobra():
    assert valor_sms(80, incluidos=100, tarifa=60) == 0

def test_ilimitado_no_cobra():
    assert valor_sms(2000, incluidos=-1, tarifa=60) == 0
```

Escribe el código **mínimo** de `valor_sms(cantidad, incluidos, tarifa)` para ponerlas en verde.

```pyreto
def valor_sms(cantidad, incluidos, tarifa):
    pass
```

:::pista
Las dos primeras pruebas se resuelven con `max(0, cantidad - incluidos) * tarifa`. La tercera necesita un caso especial antes: `if incluidos == -1: return 0`.
:::

```pyprueba
def prueba_cobra_el_exceso():
    """test_cobra_el_exceso"""
    requiere("valor_sms")
    igual(valor_sms(120, incluidos=100, tarifa=60), 1200)


def prueba_sin_exceso_no_cobra():
    """test_sin_exceso_no_cobra"""
    igual(valor_sms(80, incluidos=100, tarifa=60), 0)


def prueba_ilimitado_no_cobra():
    """test_ilimitado_no_cobra"""
    igual(valor_sms(2000, incluidos=-1, tarifa=60), 0)
```

```pysolucion
def valor_sms(cantidad, incluidos, tarifa):
    if incluidos == -1:
        return 0
    return max(0, cantidad - incluidos) * tarifa
```

## Cobertura: ¿qué líneas ejecutan tus pruebas?

```powershell
python -m pytest --cov=facturacion --cov-report=term-missing
```

```text
Name                       Stmts   Miss  Cover   Missing
--------------------------------------------------------
facturacion/reglas.py         42      3    93%   57-59
facturacion/facturas.py       35      0   100%
```

`Missing` dice qué líneas **ninguna prueba ejecutó**. Es una guía excelente para encontrar casos olvidados (por ejemplo, la rama del plan ilimitado).

:::error 100 % de cobertura no significa 0 errores
La cobertura dice qué líneas se **ejecutaron**, no si se **verificaron**. Una prueba sin `assert` que llama a todas las funciones da 100 % de cobertura y no prueba nada. Úsala para encontrar lo que te falta, no como meta en sí misma.
:::

## Mutantes: ¿tus pruebas atrapan errores?

Una forma más exigente de medir la calidad de las pruebas: **introducir errores a propósito** en el código (cambiar `+ 59` por `+ 60`, `>` por `>=`, borrar una línea) y ver si alguna prueba falla. Cada cambio es un **mutante**:

- Si alguna prueba falla, el mutante quedó **atrapado** ✅.
- Si todas pasan, el mutante **sobrevivió**: hay un error posible que tus pruebas no detectarían ❌.

Así se comprueban tus pruebas en los ejercicios de este módulo. Existen herramientas que lo hacen automáticamente sobre proyectos completos, como `mutmut`.

## Cuestionario

? La regla es "descuento para clientes con alta antes del 2023-09-01". ¿Qué fechas son los mejores casos borde?
- [ ] 2010-01-01 y 2026-01-01
- [x] 2023-08-31 y 2023-09-01
- [ ] Solo 2023-09-01
- [ ] Cualquier fecha aleatoria
> Los errores típicos (`<` en lugar de `<=`) solo aparecen justo en el límite.

? Encontraste un error en producción. ¿Qué haces primero según la práctica de regresión?
- [ ] Arreglarlo rápido
- [x] Escribir una prueba que reproduzca el error y verificar que falla
- [ ] Borrar las pruebas que fallan
- [ ] Subir la cobertura al 100 %
> La prueba demuestra el error, confirma el arreglo y evita que vuelva.

? Tus pruebas tienen 100 % de cobertura. ¿Qué significa?
- [ ] Que el código no tiene errores
- [x] Que todas las líneas se ejecutaron al menos una vez durante las pruebas
- [ ] Que todas las pruebas pasan
- [ ] Que no hace falta escribir más pruebas
> Ejecutar una línea no es verificar su resultado. La cobertura es una pista, no una garantía.
