Python no te obliga a declarar tipos, pero puedes **anotarlos**. Las anotaciones (*type hints*) no cambian lo que hace el código: son documentación que las herramientas entienden.

## Anotar parámetros y retorno

```pyrun
from decimal import Decimal


def minutos_facturables(segundos: int) -> int:
    return (segundos + 59) // 60


def calcular_iva(subtotal: Decimal, tasa: Decimal = Decimal("0.19")) -> Decimal:
    return subtotal * tasa


print(minutos_facturables(125))
print(calcular_iva(Decimal(40940)))
print(minutos_facturables.__annotations__)
```

Con anotaciones, VS Code (Pylance) te avisa **mientras escribes** si pasas un texto donde va un número, y autocompleta los métodos correctos del valor devuelto.

## Los tipos más comunes

| Anotación | Significa | Ejemplo |
|---|---|---|
| `int`, `float`, `str`, `bool` | Tipos básicos | `def es_valido(linea: str) -> bool:` |
| `list[int]` | Lista de enteros | `duraciones: list[int]` |
| `dict[str, int]` | Diccionario de texto a entero | `tarifas: dict[str, int]` |
| `tuple[str, int]` | Tupla de exactamente texto y entero | `-> tuple[int, int]` |
| `set[str]` | Conjunto de textos | `lineas: set[str]` |
| `X \| None` | `X` o `None` | `-> int \| None` |
| `None` | No devuelve nada | `def imprimir(...) -> None:` |

```pyrun
def tarifa_minuto(destino: str, tarifas: dict[str, int]) -> int | None:
    return tarifas.get(destino.strip().upper())


def separar(segundos: int) -> tuple[int, int]:
    return segundos // 60, segundos % 60


print(tarifa_minuto(" local ", {"LOCAL": 100}))
print(separar(125))
```

:::reto Anota las firmas
Agrega las anotaciones de tipo a estas dos funciones, sin cambiar lo que hacen:

- `plan_de(linea, planes)`: `linea` es texto, `planes` es un diccionario de texto a texto, y devuelve texto **o** `None`.
- `minutos_por_linea(cdrs)`: `cdrs` es una lista de tuplas `(texto, entero)` y devuelve un diccionario de texto a entero.

```pyreto
def plan_de(linea, planes):
    return planes.get(linea)


def minutos_por_linea(cdrs):
    totales = {}
    for linea, minutos in cdrs:
        totales[linea] = totales.get(linea, 0) + minutos
    return totales


print(plan_de.__annotations__)
print(minutos_por_linea.__annotations__)
```

:::pista
Una tupla de texto y entero es `tuple[str, int]`, así que una lista de ellas es `list[tuple[str, int]]`. "Texto o None" es `str | None`.
:::

```pyprueba
def prueba_plan_de():
    """plan_de está anotada: (str, dict[str, str]) -> str | None"""
    requiere("plan_de")
    igual(plan_de.__annotations__, {"linea": str, "planes": dict[str, str], "return": str | None})


def prueba_minutos_por_linea():
    """minutos_por_linea está anotada: list[tuple[str, int]] -> dict[str, int]"""
    requiere("minutos_por_linea")
    igual(minutos_por_linea.__annotations__, {"cdrs": list[tuple[str, int]], "return": dict[str, int]})


def prueba_sigue_funcionando():
    """Las funciones hacen lo mismo que antes"""
    igual(plan_de("3001", {"3001": "HOG30"}), "HOG30")
    igual(plan_de("3999", {"3001": "HOG30"}), None)
    igual(minutos_por_linea([("3001", 3), ("3002", 1), ("3001", 2)]), {"3001": 5, "3002": 1})
```

```pysolucion
def plan_de(linea: str, planes: dict[str, str]) -> str | None:
    return planes.get(linea)


def minutos_por_linea(cdrs: list[tuple[str, int]]) -> dict[str, int]:
    totales = {}
    for linea, minutos in cdrs:
        totales[linea] = totales.get(linea, 0) + minutos
    return totales


print(plan_de.__annotations__)
print(minutos_por_linea.__annotations__)
```
:::

:::capo Python no comprueba los tipos al ejecutar
`minutos_facturables("125")` no da error por la anotación: da error porque no se puede sumar texto y número. Las anotaciones las revisan herramientas como **Pylance** (mientras escribes) y **mypy** (en el módulo 20, de forma automática antes de cada commit).
:::

## Docstrings

Un **docstring** es el texto entre triples comillas justo debajo del `def`. Explica **qué** hace la función, no **cómo**:

```pyrun
def valor_exceso(consumido: int, incluido: int, tarifa: int) -> int:
    """Calcula el valor a cobrar por el consumo que excede lo incluido en el plan.

    Args:
        consumido: Unidades consumidas (minutos, megas o SMS).
        incluido: Unidades incluidas en el plan. -1 significa ilimitado.
        tarifa: Precio de cada unidad adicional, en pesos.

    Returns:
        El valor del exceso en pesos. Nunca es negativo.

    Example:
        >>> valor_exceso(342, 300, 120)
        5040
    """
    if incluido == -1:
        return 0
    return max(0, consumido - incluido) * tarifa


help(valor_exceso)
```

`help()` muestra el docstring, y VS Code lo despliega al pasar el mouse sobre la función. Este formato (secciones `Args`, `Returns`) es el **estilo Google**, uno de los más usados.

:::reto Documenta la regla
Escribe un docstring en estilo Google para esta función. Debe tener:

- una primera línea que diga qué hace;
- la sección `Args:` con el parámetro `segundos`;
- la sección `Returns:`, explicando que los minutos se cobran por minuto iniciado.

```pyreto
def minutos_facturables(segundos: int) -> int:
    return (segundos + 59) // 60


help(minutos_facturables)
```

:::pista
El docstring va justo debajo del `def`, entre triples comillas `"""`, con la misma sangría que el cuerpo. Copia la forma del ejemplo `valor_exceso`.
:::

```pyprueba
def prueba_tiene_docstring():
    """La función tiene docstring"""
    requiere("minutos_facturables")
    assert minutos_facturables.__doc__ and minutos_facturables.__doc__.strip(), "Falta el docstring (texto entre triples comillas debajo del def)"


def prueba_secciones():
    """El docstring tiene Args (con segundos) y Returns"""
    doc = minutos_facturables.__doc__ or ""
    assert "Args:" in doc, "Falta la sección Args:"
    assert "segundos" in doc.split("Args:")[1], "En Args: describe el parámetro segundos"
    assert "Returns:" in doc, "Falta la sección Returns:"


def prueba_menciona_regla():
    """Explica la regla del minuto iniciado"""
    doc = (minutos_facturables.__doc__ or "").lower()
    assert "iniciado" in doc, "Explica que se cobra por minuto iniciado"


def prueba_sigue_funcionando():
    """La función hace lo mismo"""
    igual(minutos_facturables(125), 3)
    igual(minutos_facturables(0), 0)
```

```pysolucion
def minutos_facturables(segundos: int) -> int:
    """Convierte la duración de una llamada en minutos a cobrar.

    Args:
        segundos: Duración de la llamada en segundos.

    Returns:
        Los minutos facturables: se cobra cada minuto iniciado como completo.
    """
    return (segundos + 59) // 60


help(minutos_facturables)
```
:::

:::consejo ¿Cuánto documentar?
- Funciones públicas y reglas de negocio: docstring completo.
- Funciones auxiliares obvias (`es_par(n)`): una línea o nada.
- Comentarios `#`: para explicar **por qué** algo no obvio está así, no para repetir lo que el código ya dice.
:::

:::comparar
:::mal Comentarios que repiten el código
```python
# suma 59 y divide entre 60
minutos = (segundos + 59) // 60
```
:::
:::bien Comentarios que explican el porqué
```python
# Las llamadas se cobran por minuto iniciado (regla comercial).
minutos = (segundos + 59) // 60
```
:::
:::

:::telco Documentar reglas de negocio
En facturación, el docstring es el lugar ideal para citar la regla: "Según la resolución X, el descuento aplica a clientes con tres años o más". Cuando auditoría o un compañero pregunte por qué se cobra así, la respuesta está junto al código que lo hace.
:::

## Cuestionario

? ¿Qué pasa al ejecutar `minutos_facturables(12.5)` si la función está anotada como `(segundos: int) -> int`?
- [ ] Python lanza un error de tipo por la anotación
- [x] Se ejecuta normalmente; la anotación no se comprueba al ejecutar
- [ ] Python convierte 12.5 a 12
- [ ] La función devuelve `None`
> Las anotaciones son información para herramientas como Pylance y mypy; Python no las verifica en tiempo de ejecución.

? ¿Cómo anotas una función que devuelve un entero o `None`?
- [ ] `-> int or None`
- [x] `-> int | None`
- [ ] `-> [int, None]`
- [ ] `-> int?`
> Desde Python 3.10, `|` une tipos: `int | None` significa "entero o None".

? ¿Qué debería explicar un buen comentario?
- [ ] Lo que hace cada línea, paso a paso
- [x] Por qué el código hace algo que no es obvio
- [ ] El nombre del autor y la fecha
- [ ] Nada: los comentarios siempre sobran
> El código ya dice qué hace. El comentario aporta el contexto que el código no puede expresar: la regla de negocio, la razón de una decisión.
