Tu pipeline del proyecto final necesita dos cosas corriendo juntas: la aplicación y PostgreSQL. Escribir dos `docker run` largos cada vez es incómodo y propenso a errores. **Docker Compose** los describe en un archivo.

## compose.yaml

```yaml
# compose.yaml
services:
  bd:
    image: postgres:16
    environment:
      POSTGRES_DB: facturacion
      POSTGRES_USER: telco
      POSTGRES_PASSWORD: ${PG_PASSWORD:?Define PG_PASSWORD en .env}
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5433:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U telco -d facturacion"]
      interval: 5s
      timeout: 3s
      retries: 10

  app:
    build: .
    depends_on:
      bd:
        condition: service_healthy
    environment:
      TELCO_DB_URL: postgresql+psycopg://telco:${PG_PASSWORD}@bd:5432/facturacion
      TELCO_PERIODO: ${TELCO_PERIODO:-202609}
    volumes:
      - ./datos:/datos:ro
      - ./salidas:/salidas
    command: ["conciliar", "/datos", "--salida", "/salidas"]

volumes:
  pgdata:
```

| Clave | Significa |
|---|---|
| `services` | Cada contenedor del sistema, con su nombre (`bd`, `app`) |
| `image` / `build` | Usar una imagen existente / construir con el `Dockerfile` de esa carpeta |
| `environment` | Variables de entorno. `${VAR}` se toma de tu entorno o del `.env` junto al compose |
| `${VAR:-202609}` | Valor por defecto si no está definida |
| `${VAR:?mensaje}` | Error con ese mensaje si no está definida |
| `healthcheck` | Cómo saber si el servicio está **listo**, no solo arrancado |
| `depends_on` + `service_healthy` | `app` arranca cuando `bd` responde, no antes |
| `volumes` (al final) | Volúmenes con nombre: los datos de PostgreSQL sobreviven a `docker compose down` |

En la URL de la aplicación, el servidor es **`bd`**: el nombre del servicio. Compose crea una red donde cada servicio se encuentra por su nombre.

:::reto Tu compose.yaml
Escribe en `compose` un archivo con dos servicios (las pruebas lo leen con `yaml.safe_load`):

- `bd`: imagen `postgres:16`, la contraseña tomada de `${PG_PASSWORD}`, el volumen con nombre `pgdata` en `/var/lib/postgresql/data` y un `healthcheck` con `pg_isready`;
- `app`: se construye con el `Dockerfile` de la carpeta (`build: .`), **espera a que `bd` esté sana** y recibe `TELCO_DB_URL` apuntando al servidor `bd` en el puerto **5432** (no a `localhost`);
- y declara el volumen `pgdata` al final.

```pyreto
compose = """
services:
  bd:
    image: postgres:16

"""
```

:::pista
Toma el `compose.yaml` de arriba como modelo. Lo importante: `depends_on: bd: condition: service_healthy` en `app`, y en su URL `@bd:5432`.
:::

```pyprueba
import yaml


def _leer():
    try:
        datos = yaml.safe_load(compose)
    except yaml.YAMLError as e:
        raise AssertionError(f"El YAML tiene un error de formato: {e}") from None
    assert isinstance(datos, dict) and "services" in datos, "Falta la sección services"
    return datos


def prueba_bd():
    """bd: imagen, volumen y healthcheck"""
    bd = _leer()["services"].get("bd", {})
    igual(bd.get("image"), "postgres:16", "image")
    assert any(str(v).startswith("pgdata:") for v in bd.get("volumes", [])), "Monta el volumen pgdata"
    assert "pg_isready" in str(bd.get("healthcheck", {}).get("test", "")), "El healthcheck debe usar pg_isready"
    assert "${PG_PASSWORD" in str(bd.get("environment", "")), "Toma la contraseña de ${PG_PASSWORD}"


def prueba_app():
    """app: build, espera a bd sana y usa bd:5432"""
    app = _leer()["services"].get("app", {})
    igual(app.get("build"), ".", "build")
    igual(app.get("depends_on", {}).get("bd", {}).get("condition") if isinstance(app.get("depends_on"), dict) else None,
          "service_healthy", "depends_on.bd.condition")
    entorno = app.get("environment", {})
    url = entorno.get("TELCO_DB_URL", "") if isinstance(entorno, dict) else " ".join(entorno)
    assert "@bd:5432" in url, f"TELCO_DB_URL debe apuntar a bd:5432: {url}"
    assert "localhost" not in url, "Dentro de Compose, localhost es el propio contenedor"


def prueba_volumen():
    """Declara el volumen pgdata"""
    assert "pgdata" in (_leer().get("volumes") or {}), "Declara pgdata en la sección volumes del final"
```

## Comandos

```powershell
docker compose up -d bd                    # solo la base, en segundo plano
docker compose ps                          # estado (y salud) de los servicios
docker compose run --rm app validar /datos # una tarea puntual con la app
docker compose up --build                  # todo, reconstruyendo la imagen de app
docker compose logs -f app
docker compose down                        # detiene y borra contenedores (no los volúmenes)
docker compose down -v                     # ...y también los volúmenes: ¡borra la base!
```

:::consejo Arrancado no es listo
PostgreSQL tarda unos segundos en aceptar conexiones después de que su contenedor arranca. Sin `healthcheck`, tu aplicación intentaría conectarse antes y fallaría "a veces". Además de `service_healthy`, conviene que la aplicación **reintente** la conexión unos segundos al arrancar (lo harás en el ejercicio 9): en producción, la base puede reiniciarse en cualquier momento.
:::

## Entornos de desarrollo en contenedores (devcontainers)

Un **devcontainer** es un contenedor configurado para **desarrollar**: VS Code se conecta a él y trabajas como si fuera tu máquina, con Python, librerías y extensiones ya instalados. Se define en `.devcontainer/devcontainer.json`:

```json
{
  "name": "PyDatos",
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "postCreateCommand": "pip install -r requirements.txt",
  "forwardPorts": [8000],
  "customizations": {
    "vscode": {
      "extensions": ["ms-python.python", "charliermarsh.ruff", "ms-toolsai.jupyter"]
    }
  }
}
```

**GitHub Codespaces** usa ese archivo para crear el entorno **en la nube**: desde la página del repositorio, *Code → Codespaces → Create codespace*, y en un minuto tienes VS Code en el navegador, con Docker disponible adentro. Las cuentas personales tienen horas gratuitas al mes. Es la forma de practicar los módulos 22 y el proyecto final desde la oficina sin instalar nada (recuerda: **sin** datos reales de la empresa en un servicio externo; usa los datos generados).

:::telco El mismo entorno para todo el equipo
Con un `compose.yaml` y un `devcontainer.json` en el repositorio, alguien nuevo en el equipo pasa de "clonar el repositorio" a "tengo PostgreSQL, las librerías y las extensiones funcionando" en minutos, en lugar de un día de instalaciones y "a mí no me funciona".
:::

## Cuestionario

? En `compose.yaml`, ¿cómo se conecta `app` al PostgreSQL del servicio `bd`?
- [ ] `localhost:5433`
- [x] `bd:5432`
- [ ] `host.docker.internal:5432`
- [ ] Por un archivo compartido
> Dentro de la red de Compose, cada servicio se encuentra por su nombre y el puerto interno.

? ¿Qué logra `depends_on` con `condition: service_healthy`?
- [ ] Que bd se reinicie si falla
- [x] Que app arranque solo cuando el healthcheck de bd indica que está listo
- [ ] Que ambos usen el mismo volumen
- [ ] Que app se construya antes
> Evita que la aplicación se conecte a una base que todavía está arrancando.

? ¿Qué hace `docker compose down -v`?
- [ ] Solo detiene los contenedores
- [x] Detiene y borra los contenedores y también los volúmenes con nombre (los datos de la base)
- [ ] Muestra la versión
- [ ] Borra las imágenes
> Útil para empezar de cero; peligroso si la base tenía datos que querías conservar.
