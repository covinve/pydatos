Las pruebas unitarias verifican piezas aisladas con dobles. Pero ¿el adaptador SQLite funciona de verdad con SQLite? ¿La CLI lee bien el CSV en latin-1? Eso lo responden las **pruebas de integración**: las piezas reales, juntas, con archivos y bases de verdad (temporales).

## conftest.py: fixtures compartidos

Los *fixtures* definidos en `tests/conftest.py` están disponibles en todas las pruebas de esa carpeta, sin importarlos:

```python
# tests/conftest.py
import shutil
import sqlite3
from pathlib import Path

import pytest

DATOS = Path(__file__).parent / "datos_prueba"


@pytest.fixture(scope="session")
def datos_prueba():
    """La carpeta con la muestra (solo lectura)."""
    return DATOS


@pytest.fixture
def carpeta_trabajo(tmp_path):
    """Una copia de los datos de prueba que cada prueba puede modificar."""
    destino = tmp_path / "datos"
    shutil.copytree(DATOS, destino)
    return destino


@pytest.fixture
def bd(tmp_path):
    con = sqlite3.connect(tmp_path / "prueba.db")
    yield con                      # lo que va después del yield es la limpieza
    con.close()
```

| `scope=` | El fixture se crea… |
|---|---|
| `"function"` (por defecto) | Una vez por prueba: aislamiento total |
| `"module"` | Una vez por archivo de pruebas |
| `"session"` | Una vez por toda la ejecución: para cosas caras y de solo lectura |

## Marcadores

Las pruebas lentas no deberían correr en cada cambio:

```python
import pytest

@pytest.mark.lento
def test_carga_de_un_millon_de_filas(tmp_path):
    ...

@pytest.mark.skipif("TELCO_DB_URL" not in os.environ, reason="sin PostgreSQL")
def test_postgres():
    ...
```

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
markers = ["lento: pruebas que tardan más de unos segundos"]
addopts = "-m 'not lento'"          # por defecto, sin las lentas
```

`pytest -m lento` corre solo las lentas; `pytest -m ""` corre todas.

## Parametrizar en serio

```python
@pytest.mark.parametrize(
    ("segundos", "minutos"),
    [(0, 0), (1, 1), (59, 1), (60, 1), (61, 2), (3600, 60)],
    ids=["cero", "un-segundo", "casi-minuto", "minuto-exacto", "minuto-y-uno", "una-hora"],
)
def test_minutos_facturables(segundos, minutos):
    assert minutos_facturables(segundos) == minutos
```

Con `ids`, un fallo se lee `test_minutos_facturables[minuto-exacto]` en lugar de `[60-1]`.

## Cobertura

`pytest-cov` mide qué líneas ejecutaron tus pruebas:

```powershell
pytest --cov=src/conciliacion --cov-report=term-missing
```

```text
Name                          Stmts   Miss  Cover   Missing
-----------------------------------------------------------
src/conciliacion/reglas.py       42      0   100%
src/conciliacion/lectura.py      38      6    84%   51-53, 77-79
src/conciliacion/cli.py          25     25     0%
-----------------------------------------------------------
TOTAL                           105     31    70%
```

`Missing` te dice qué líneas nunca se ejecutaron: casi siempre son los caminos de error (`except`, el `if` raro). Agrega `--cov-report=html` y abre `htmlcov/index.html` para verlas marcadas en rojo.

:::capo 100 % de cobertura no es 100 % correcto
La cobertura dice qué líneas **se ejecutaron**, no qué se **verificó**. Una prueba sin `assert` sube la cobertura sin probar nada. Úsala para encontrar lo **no probado**, no como meta. Un objetivo razonable: dominio cerca del 100 %, el resto por encima de 80 %. Las pruebas de mutantes del módulo 10 miden algo más honesto: si tus pruebas **detectan** errores.
:::

- [ ] Que no tiene errores
