Saber **cómo** crear módulos es fácil. Lo difícil es decidir **qué** va en cada uno. Dos ideas guían esa decisión.

## Alta cohesión

Un módulo es **cohesivo** cuando todo lo que contiene trata de lo mismo. `lectura.py` lee archivos; no calcula IVA ni dibuja gráficos.

:::comparar
:::mal Módulos por "tipo de cosa"
```text
utils.py       ← 40 funciones sin relación
helpers.py     ← otras 30
funciones.py   ← y otras 25
```
:::
:::bien Módulos por responsabilidad
```text
lectura.py     ← leer y parsear archivos
reglas.py      ← validación y tarificación
facturas.py    ← cálculo de facturas
reportes.py    ← salidas para personas
```
:::
:::

:::consejo La prueba del nombre
Si no puedes describir un módulo en una frase sin usar "y", tiene más de una responsabilidad. `utils.py` es casi siempre una señal de que falta pensar dónde va cada cosa.
:::

## Bajo acoplamiento

Dos módulos están **acoplados** cuando cambiar uno obliga a cambiar el otro. Se reduce el acoplamiento cuando cada módulo **depende de lo mínimo** del otro:

| Acoplado | Desacoplado |
|---|---|
| `reglas.py` abre el archivo de clientes por su cuenta | `reglas.py` recibe el conjunto de líneas ya cargado |
| `facturas.py` imprime el resultado | `facturas.py` devuelve el resultado; otro módulo decide cómo mostrarlo |
| Todos leen la constante `RUTA_DATOS` | La ruta llega como parámetro desde el programa principal |

Recuerda las funciones puras del módulo 5: las reglas de negocio que **reciben** sus datos y **devuelven** resultados son las más fáciles de reutilizar, probar y mover de lugar.

:::reto Desacopla la regla
`es_de_cliente` abre `clientes.csv` **cada vez** que la llamas: con un millón de CDR, abriría el archivo un millón de veces, y no se puede probar sin ese archivo. Sepáralo en dos funciones:

- `cargar_lineas(ruta)`: lee el archivo **una vez** y devuelve el **conjunto** de líneas de los clientes (la columna 9, `linea`);
- `es_de_cliente(linea, lineas_clientes)`: regla pura, sin abrir archivos.

```pyreto
def es_de_cliente(linea):
    with open("clientes.csv", encoding="latin-1") as f:
        next(f)
        for fila in f:
            if fila.rstrip("\n").split(",")[8] == linea:
                return True
    return False


print(es_de_cliente("3163561908"))
```

:::pista
Mueve el `with open(...)` a `cargar_lineas`, y que agregue cada línea a un `set()` que devuelves al final. `es_de_cliente` queda en una línea: `return linea in lineas_clientes`.
:::

```pyprueba
import ast


def prueba_cargar():
    """cargar_lineas devuelve el conjunto de líneas de clientes.csv"""
    requiere("cargar_lineas")
    lineas = cargar_lineas("clientes.csv")
    assert isinstance(lineas, set), f"Debe devolver un set, devolvió {type(lineas).__name__}"
    igual(len(lineas), 40, "cantidad de líneas")
    assert "3163561908" in lineas, "Falta la línea 3163561908 del primer cliente"


def prueba_regla_pura():
    """es_de_cliente usa el conjunto que recibe"""
    requiere("es_de_cliente")
    igual(es_de_cliente("3001", {"3001", "3002"}), True)
    igual(es_de_cliente("3999", {"3001", "3002"}), False)


def prueba_sin_archivos():
    """es_de_cliente no abre archivos"""
    funcion = next(n for n in ast.walk(ast.parse(codigo)) if isinstance(n, ast.FunctionDef) and n.name == "es_de_cliente")
    llamadas = {n.func.id for n in ast.walk(funcion) if isinstance(n, ast.Call) and isinstance(n.func, ast.Name)}
    assert "open" not in llamadas, "es_de_cliente no debe abrir el archivo"
```

```pysolucion
def cargar_lineas(ruta):
    lineas = set()
    with open(ruta, encoding="latin-1") as f:
        next(f)
        for fila in f:
            lineas.add(fila.rstrip("\n").split(",")[8])
    return lineas


def es_de_cliente(linea, lineas_clientes):
    return linea in lineas_clientes


LINEAS = cargar_lineas("clientes.csv")
print(es_de_cliente("3163561908", LINEAS))
```
:::

## La dirección de las dependencias

```text
cli.py   (programa principal: argumentos y logging)
   │
   ├──► lectura.py    (habla con los archivos)
   ├──► reportes.py   (habla con las personas)
   │        │
   ▼        ▼
facturas.py ──► reglas.py    (lógica de negocio pura: no lee ni imprime nada)
```

Las flechas van siempre **hacia abajo**: `reglas.py` no importa a nadie del proyecto, y nadie importa a `cli.py`.

Una buena regla: **lo que habla con el mundo exterior (archivos, pantalla, bases de datos) depende de la lógica de negocio, nunca al revés**. Lo verás con detalle en el módulo 19.

## Estructura de un proyecto de datos

```text
mi-proyecto/
├── pyproject.toml         ← descripción y dependencias
├── README.md              ← qué es, cómo se instala y cómo se usa
├── .gitignore
├── src/
│   └── mi_proyecto/
│       ├── __init__.py
│       ├── __main__.py    ← permite `python -m mi_proyecto`
│       ├── cli.py         ← argumentos de terminal
│       ├── lectura.py
│       ├── reglas.py
│       └── reportes.py
├── tests/                 ← una prueba por módulo (módulo 10)
├── notebooks/             ← exploración (no es código de producción)
└── datos/                 ← en .gitignore
```

:::telco Notebooks y módulos juntos
Un patrón muy productivo en datos: la lógica vive en `src/` y el notebook **importa** desde ahí (`from mi_proyecto.reglas import clasificar`). Exploras en el notebook, y cuando algo funciona, lo mueves al paquete con sus pruebas. Con la instalación editable, el notebook ve los cambios al instante (agrega `%load_ext autoreload` y `%autoreload 2` en la primera celda).
:::

## Cuestionario

? ¿Qué módulo tiene mejor cohesión?
- [ ] `utils.py` con funciones de lectura, formato, IVA y gráficos
- [x] `tarificacion.py` con las funciones que calculan el valor de los consumos
- [ ] `funciones.py` con todo lo que no cupo en otro lado
- [ ] `varios.py`
> Un módulo cohesivo agrupa funciones que tratan de lo mismo.

? `reglas.py` abre `clientes.csv` cada vez que valida un CDR. ¿Cuál es el problema de diseño?
- [ ] Ninguno
- [x] Las reglas quedan acopladas al archivo; deberían recibir las líneas de clientes ya cargadas
- [ ] Debería abrirlo con encoding utf-8
- [ ] Debería usar `import *`
> Además de lento, mezcla la lógica de negocio con la lectura de archivos: no se puede probar ni reutilizar sin ese archivo.

? En un proyecto bien organizado, ¿cuál dependencia es correcta?
- [x] `cli.py` (programa principal) importa de `reglas.py`
- [ ] `reglas.py` importa de `cli.py`
- [ ] `reglas.py` imprime en pantalla
- [ ] Todos los módulos se importan entre sí
> El programa principal usa la lógica de negocio; la lógica no sabe nada de cómo se ejecuta el programa.
