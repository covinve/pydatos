Un **Dockerfile** es la receta de la imagen: una lista de instrucciones que Docker ejecuta en orden.

```dockerfile
# Dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

COPY requirements.lock .
RUN pip install --no-cache-dir -r requirements.lock

COPY src/ src/
COPY pyproject.toml .
RUN pip install --no-cache-dir --no-deps .

RUN useradd --create-home telco
USER telco

ENTRYPOINT ["python", "-m", "conciliacion.cli"]
CMD ["--help"]
```

| Instrucción | Para qué |
|---|---|
| `FROM` | Imagen base. `-slim` pesa ~50 MB en lugar de ~400 MB |
| `ENV` | Variables de entorno de la imagen. `PYTHONUNBUFFERED=1` hace que los `print` se vean de inmediato en `docker logs` |
| `WORKDIR` | Carpeta de trabajo (la crea si no existe) |
| `COPY origen destino` | Copia archivos de tu proyecto a la imagen |
| `RUN` | Ejecuta un comando **al construir** (instalar librerías) |
| `USER` | Con qué usuario corre el contenedor |
| `ENTRYPOINT` | El programa que ejecuta el contenedor |
| `CMD` | Argumentos por defecto (se reemplazan con lo que escribas después de la imagen en `docker run`) |

```powershell
docker build -t telco-pipeline:1.0 .
docker run --rm telco-pipeline:1.0                    # muestra --help
docker run --rm telco-pipeline:1.0 validar /datos     # reemplaza el CMD
```

## Capas y caché: el orden importa

:::pasos Cada instrucción es una capa
:::paso Docker guarda cada paso
Cada `COPY` y `RUN` produce una **capa**. Al reconstruir, Docker reutiliza las capas cuyas entradas no cambiaron.
:::
:::paso Si una capa cambia, las siguientes se rehacen
Si copias **todo** el proyecto antes de instalar (`COPY . .` y luego `pip install`), cualquier cambio en una línea de código invalida la capa de instalación: cada construcción reinstala pandas, numpy, duckdb… (minutos).
:::
:::paso Lo que cambia poco, primero
Copiando primero **solo** `requirements.lock` e instalando, esa capa se reutiliza mientras no cambien las dependencias. Cambiar tu código solo rehace las últimas capas: segundos.
:::
:::

## No correr como root

Por defecto, el contenedor corre como **root**. Si tu programa tiene un error de seguridad (o un archivo malicioso se procesa), el daño posible es mucho mayor. `useradd` + `USER` es una práctica estándar y casi gratuita.

## ENTRYPOINT en forma de lista

:::comparar
:::mal Forma de texto
```dockerfile
ENTRYPOINT python -m conciliacion.cli
```
Se ejecuta a través de un *shell* (`/bin/sh -c ...`): tu programa no recibe las señales de `docker stop` (se mata a los 10 segundos sin cerrar archivos ni conexiones) y no puedes pasarle argumentos.
:::
:::bien Forma de lista (exec)
```dockerfile
ENTRYPOINT ["python", "-m", "conciliacion.cli"]
```
Tu programa es el proceso principal, recibe las señales y los argumentos de `docker run imagen ...` se le agregan.
:::
:::

## .dockerignore

Antes de construir, Docker envía la carpeta del proyecto (el **contexto**) al motor. Sin `.dockerignore`, eso incluye `.venv/`, `.git/`… y **tus 20 GB de datos**.

```text
# .dockerignore
.git
.venv
__pycache__/
*.pyc
.pytest_cache/
.mypy_cache/
datos/
salidas/
*.csv
*.parquet
.env
```

:::error Nunca datos ni secretos en la imagen
Una imagen se comparte (un registro, otro equipo, un servidor). Los datos de clientes y el `.env` con contraseñas **no** deben estar dentro: los datos entran por **volúmenes** y los secretos por **variables de entorno** al ejecutar (lección 3). `.dockerignore` es la barrera para que no entren por accidente.
:::

## Cuestionario

? ¿Por qué se copia `requirements.lock` e instala ANTES de copiar el código?
- [ ] Porque Docker lo exige
- [x] Para que la capa de instalación se reutilice de la caché mientras las dependencias no cambien
- [ ] Para que la imagen pese menos
- [ ] Para correr como usuario sin privilegios
> Cambiar el código ya no obliga a reinstalar todas las librerías en cada construcción.

? ¿Qué ventaja tiene `ENTRYPOINT ["python", "-m", "app"]` frente a `ENTRYPOINT python -m app`?
- [ ] Ninguna
- [x] El programa recibe directamente las señales (como `docker stop`) y los argumentos de `docker run`
- [ ] Es más rápido de construir
- [ ] Permite usar variables de entorno
> La forma de texto pasa por un shell intermedio que se queda con las señales.

? ¿Para qué sirve `.dockerignore`?
- [ ] Para ignorar errores de construcción
- [x] Para excluir del contexto de construcción archivos como `.venv`, datos y `.env`
- [ ] Para ocultar la imagen
- [ ] Para ignorar contenedores detenidos
> Construcciones más rápidas, imágenes más livianas y sin datos ni secretos.
