Escribir pruebas es fácil. Escribir **buenas** pruebas, las que atrapan errores reales, requiere pensar qué casos elegir.

## Clases de equivalencia

Agrupa las entradas posibles en **clases** que el código trata igual, y prueba al menos un caso de cada una. Para `minutos_facturables(segundos)`:

| Clase | Ejemplo |
|---|---|
| Cero (no contestada) | 0 |
| Menos de un minuto | 1, 30, 59 |
| Minuto exacto | 60, 120 |
| Un poco más de un minuto | 61 |
| Llamada larga | 3600 |

## Casos borde: donde viven los errores

Los errores se esconden en los **límites**: el último valor que no se cobra y el primero que sí; la lista vacía; el plan ilimitado; la fecha de corte exacta.

| Regla | Casos borde |
|---|---|
| "El exceso se cobra por encima de lo incluido" | consumo = incluido, incluido + 1 |
| "Descuento a quien se dio de alta antes del 2023-09-01" | 2023-08-31 y 2023-09-01 exactos |
| "Franja nocturna de 22:00 a 05:59" | 21:59, 22:00, 05:59, 06:00 |
| Cualquier lista | vacía, un elemento, muchos |
| Ilimitado = -1 | -1, 0 |

:::consejo Pregunta "¿qué pasaría si…?"
¿Y si la lista está vacía? ¿Y si el número es negativo? ¿Y si el texto tiene espacios? ¿Y si la fecha es el 29 de febrero? Cada respuesta que te haga dudar es una prueba que vale la pena escribir.
:::

## Pruebas de regresión

Cuando encuentras un error, **antes de arreglarlo** escribe una prueba que lo reproduzca (debe fallar). Luego arréglalo (la prueba pasa). Esa prueba queda para siempre: si alguien reintroduce el error, la prueba lo atrapa.

```python
def test_regresion_iva_de_150_redondea_hacia_arriba():
    """Ticket FAC-231: el IVA de $150 se calculaba como $28 en lugar de $29."""
    assert calcular_iva(150) == 29
```

## El ciclo TDD: rojo, verde, refactorizar

En el **desarrollo guiado por pruebas** (*Test-Driven Development*) escribes la prueba **antes** que el código:

:::pasos El ciclo TDD
:::paso 🔴 Rojo: escribe una prueba que falle
```python
def test_valor_sms_cobra_exceso():
    assert valor_sms(120, incluidos=100, tarifa=60) == 1200
```
Todavía no existe `valor_sms`: la prueba falla. Eso confirma que la prueba sirve para algo.
:::
:::paso 🟢 Verde: el código mínimo para que pase
```python
def valor_sms(cantidad, incluidos, tarifa):
    return max(0, cantidad - incluidos) * tarifa
```
No te adelantes: escribe solo lo necesario para la prueba actual.
:::
:::paso 🔵 Refactoriza con red de seguridad
Con la prueba en verde, mejora el código (nombres, duplicación, estructura). Si algo se rompe, la prueba te avisa al instante.
:::
:::paso 🔁 Repite con el siguiente caso
```python
def test_valor_sms_ilimitado_no_cobra():
    assert valor_sms(2000, incluidos=-1, tarifa=0) == 0
```
Rojo de nuevo. Agregas el caso del ilimitado, verde, refactorizas… y así hasta cubrir la regla completa.
:::
:::

TDD no es obligatorio, pero practicarlo cambia la forma de pensar: te obliga a definir **qué** debe hacer el código antes de pensar **cómo**.

## Cobertura: ¿qué líneas ejecutan tus pruebas?

```powershell
python -m pytest --cov=facturacion --cov-report=term-missing
```

```text
Name                       Stmts   Miss  Cover   Missing
--------------------------------------------------------
facturacion/reglas.py         42      3    93%   57-59
facturacion/facturas.py       35      0   100%
```

`Missing` dice qué líneas **ninguna prueba ejecutó**. Es una guía excelente para encontrar casos olvidados (por ejemplo, la rama del plan ilimitado).

:::error 100 % de cobertura no significa 0 errores
La cobertura dice qué líneas se **ejecutaron**, no si se **verificaron**. Una prueba sin `assert` que llama a todas las funciones da 100 % de cobertura y no prueba nada. Úsala para encontrar lo que te falta, no como meta en sí misma.
:::

## Mutantes: ¿tus pruebas atrapan errores?

Una forma más exigente de medir la calidad de las pruebas: **introducir errores a propósito** en el código (cambiar `+ 59` por `+ 60`, `>` por `>=`, borrar una línea) y ver si alguna prueba falla. Cada cambio es un **mutante**:

- Si alguna prueba falla, el mutante quedó **atrapado** ✅.
- Si todas pasan, el mutante **sobrevivió**: hay un error posible que tus pruebas no detectarían ❌.

Así se comprueban tus pruebas en los ejercicios de este módulo. Existen herramientas que lo hacen automáticamente sobre proyectos completos, como `mutmut`.

## Cuestionario

? La regla es "descuento para clientes con alta antes del 2023-09-01". ¿Qué fechas son los mejores casos borde?
- [ ] 2010-01-01 y 2026-01-01
- [x] 2023-08-31 y 2023-09-01
- [ ] Solo 2023-09-01
- [ ] Cualquier fecha aleatoria
> Los errores típicos (`<` en lugar de `<=`) solo aparecen justo en el límite.

? Encontraste un error en producción. ¿Qué haces primero según la práctica de regresión?
- [ ] Arreglarlo rápido
- [x] Escribir una prueba que reproduzca el error y verificar que falla
- [ ] Borrar las pruebas que fallan
- [ ] Subir la cobertura al 100 %
> La prueba demuestra el error, confirma el arreglo y evita que vuelva.

? Tus pruebas tienen 100 % de cobertura. ¿Qué significa?
- [ ] Que el código no tiene errores
- [x] Que todas las líneas se ejecutaron al menos una vez durante las pruebas
- [ ] Que todas las pruebas pasan
- [ ] Que no hace falta escribir más pruebas
> Ejecutar una línea no es verificar su resultado. La cobertura es una pista, no una garantía.
