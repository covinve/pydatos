## Herencia

Una clase puede **heredar** de otra: recibe sus atributos y métodos, y puede **sobrescribir** los que necesite cambiar.

```pyrun
class Plan:
    def __init__(self, plan_id, cargo_fijo, minutos_incluidos, tarifa_minuto):
        self.plan_id = plan_id
        self.cargo_fijo = cargo_fijo
        self.minutos_incluidos = minutos_incluidos
        self.tarifa_minuto = tarifa_minuto

    def valor_voz(self, minutos):
        return max(0, minutos - self.minutos_incluidos) * self.tarifa_minuto

    def describir(self):
        return f"{self.plan_id}: ${self.cargo_fijo} + voz ${self.valor_voz(400)} (con 400 min)"


class PlanIlimitado(Plan):
    def __init__(self, plan_id, cargo_fijo):
        super().__init__(plan_id, cargo_fijo, minutos_incluidos=-1, tarifa_minuto=0)

    def valor_voz(self, minutos):          # sobrescribe
        return 0


planes = [Plan("HOG30", 35900, 300, 120), PlanIlimitado("ILIM", 89900)]
for plan in planes:
    print(plan.describir())               # cada uno usa su propio valor_voz
print(isinstance(planes[1], Plan))
```

- `class PlanIlimitado(Plan)` declara la herencia.
- `super().__init__(...)` llama al `__init__` de la clase padre.
- `describir` está definido una sola vez en `Plan`, pero llama al `valor_voz` **de cada objeto**: eso es **polimorfismo**.

## Clases abstractas: obligar a implementar

A veces la clase padre solo define **qué** deben saber hacer sus hijas, sin implementarlo. Para eso está `abc`:

```pyrun
from abc import ABC, abstractmethod


class ReglaDeDescuento(ABC):
    @abstractmethod
    def aplicar(self, cargo_fijo: int) -> int:
        """Devuelve el descuento en pesos."""


class SinDescuento(ReglaDeDescuento):
    def aplicar(self, cargo_fijo):
        return 0


class Porcentaje(ReglaDeDescuento):
    def __init__(self, porcentaje):
        self.porcentaje = porcentaje

    def aplicar(self, cargo_fijo):
        return round(cargo_fijo * self.porcentaje / 100)


for regla in [SinDescuento(), Porcentaje(10)]:
    print(type(regla).__name__, regla.aplicar(79900))

ReglaDeDescuento()   # error esperado
```

No se puede crear un objeto de una clase abstracta, ni de una hija que olvidó implementar `aplicar`.

## Composición: "tiene un" en lugar de "es un"

La herencia expresa "**es un**": un `PlanIlimitado` *es un* `Plan`. La composición expresa "**tiene un**": una `Factura` *tiene un* cliente, *tiene un* plan y *tiene* conceptos.

```pyrun
from dataclasses import dataclass, field


@dataclass
class Cliente:
    cliente_id: str
    nombre: str


@dataclass
class Concepto:
    descripcion: str
    valor: int


@dataclass
class Factura:
    cliente: Cliente                                  # tiene un cliente
    conceptos: list[Concepto] = field(default_factory=list)

    @property
    def total(self):
        return sum(c.valor for c in self.conceptos)


f = Factura(Cliente("CL1", "Lucía Gómez"))
f.conceptos.append(Concepto("Cargo fijo HOG30", 35900))
f.conceptos.append(Concepto("Minutos adicionales", 5040))
print(f.cliente.nombre, f.total)
```

:::consejo Prefiere la composición
Las jerarquías de herencia profundas (`Plan` → `PlanPostpago` → `PlanEmpresarial` → `PlanEmpresarialPremium`…) se vuelven rígidas: un cambio arriba afecta a todos. La recomendación clásica es **"composición sobre herencia"**: arma objetos con piezas (un plan *tiene una* regla de descuento) en vez de crear una subclase por cada combinación.
:::

## Protocol: contratos sin herencia

`Protocol` (del módulo `typing`) describe **qué métodos** debe tener un objeto, sin obligarlo a heredar de nada. Cualquier clase que tenga esos métodos cumple el contrato. Es la versión formal del "si camina como pato y hace cuac, es un pato":

```pyrun
from typing import Protocol


class Tarificable(Protocol):
    def valor(self) -> int: ...


class Llamada:
    def __init__(self, segundos, tarifa):
        self.segundos, self.tarifa = segundos, tarifa

    def valor(self):
        return (self.segundos + 59) // 60 * self.tarifa


class Sms:
    def valor(self):
        return 60


def total(items: list[Tarificable]) -> int:
    return sum(item.valor() for item in items)


print(total([Llamada(125, 120), Sms(), Llamada(61, 950)]))
```

`Llamada` y `Sms` no heredan de `Tarificable`, pero las herramientas de tipos (Pylance, mypy) verifican que tengan `valor()`.

| Herramienta | Úsala cuando |
|---|---|
| Herencia | Hay una relación "es un" clara y compartes mucho comportamiento |
| ABC | Quieres obligar a que las subclases implementen ciertos métodos |
| Composición | Un objeto se arma con piezas intercambiables |
| `Protocol` | Solo te importa que el objeto sepa hacer algo, no de dónde viene |

:::telco Reglas intercambiables
Con composición y un contrato (`ReglaDeDescuento`), cambiar la política comercial es cambiar **qué objeto** se le pasa a la factura, no reescribir la factura. Es la misma idea del validador de reglas enchufables del módulo 5, ahora con objetos.
:::
