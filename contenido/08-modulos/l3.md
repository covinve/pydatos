Hasta ahora ejecutas tu código desde su carpeta y dependes de que Python lo encuentre ahí. Los proyectos profesionales se **instalan**: así se pueden importar desde cualquier lugar (las pruebas, un notebook, otro proyecto) y exponer comandos de terminal.

## El archivo pyproject.toml

`pyproject.toml` es el estándar actual para describir un proyecto de Python: nombre, versión, dependencias y cómo construirlo. Está escrito en **TOML**, un formato de configuración fácil de leer.

```toml
[project]
name = "telco-utils"
version = "0.1.0"
description = "Utilidades de facturación telco"
readme = "README.md"
requires-python = ">=3.11"
dependencies = [
    "pandas>=2.2",
]

[project.optional-dependencies]
dev = ["pytest>=8", "ruff>=0.6"]

[project.scripts]
telco-formato = "telco_utils.cli:main"

[build-system]
requires = ["setuptools>=69"]
build-backend = "setuptools.build_meta"
```

| Sección | Para qué |
|---|---|
| `[project]` | Nombre, versión, Python mínimo y dependencias que se instalan con tu paquete |
| `[project.optional-dependencies]` | Grupos opcionales, como las herramientas de desarrollo: `pip install -e ".[dev]"` |
| `[project.scripts]` | Comandos de terminal: `telco-formato` ejecutará la función `main` de `telco_utils/cli.py` |
| `[build-system]` | Qué herramienta construye el paquete (setuptools es la clásica) |

:::nota Nombre del proyecto y nombre del paquete
El **proyecto** se llama `telco-utils` (con guion, es lo que ves en `pip list`); el **paquete** que importas se llama `telco_utils` (con guion bajo, porque los nombres de Python no admiten guiones).
:::

## La estructura src/

La estructura recomendada pone el paquete dentro de una carpeta `src/`:

```text
telco-utils/
├── pyproject.toml
├── README.md
├── src/
│   └── telco_utils/
│       ├── __init__.py
│       ├── formato.py
│       └── cli.py
└── tests/
    └── test_formato.py
```

¿Por qué `src/`? Porque obliga a **instalar** el paquete para usarlo. Así las pruebas prueban lo mismo que usará cualquiera que instale el paquete, y no "lo que casualmente está en la carpeta actual".

## Instalación editable

```powershell
python -m pip install -e .
```

`-e` (*editable*) instala el proyecto **apuntando a tu carpeta**: cada cambio que hagas en el código se refleja de inmediato, sin reinstalar. Es la forma normal de trabajar en tu propio paquete.

```powershell
python -c "import telco_utils; print(telco_utils.__file__)"
pip show telco-utils
telco-formato 48719.5        # el comando que definiste en [project.scripts]
```

## Comandos de terminal propios

La función que apunta `[project.scripts]` es una función normal, que lee `sys.argv` o usa `argparse`:

```python
# src/telco_utils/cli.py
import argparse

from telco_utils.formato import formatear_pesos


def main() -> None:
    parser = argparse.ArgumentParser(description="Da formato de pesos a un valor")
    parser.add_argument("valor", type=float)
    args = parser.parse_args()
    print(formatear_pesos(args.valor))
```

Al instalar, pip crea un ejecutable `telco-formato.exe` dentro de `.venv\Scripts\`, que está en el PATH mientras el entorno está activo.

## Versionar con criterio

La convención más usada es **versionado semántico**: `MAYOR.MENOR.PARCHE`.

| Cambia | Cuándo | Ejemplo |
|---|---|---|
| PARCHE | Corriges un error sin cambiar cómo se usa | 1.4.2 → 1.4.3 |
| MENOR | Agregas funciones nuevas compatibles | 1.4.3 → 1.5.0 |
| MAYOR | Cambias algo que rompe a quien lo usa | 1.5.0 → 2.0.0 |

:::telco Tus herramientas como paquete
Si tu equipo comparte funciones (leer los CDR, calcular el IVA, formatear pesos), empaquetarlas en un `telco-utils` instalable evita que cada analista tenga su propia copia ligeramente distinta. Todos instalan la misma versión, y cuando corriges un error, todos lo reciben al actualizar.
:::
