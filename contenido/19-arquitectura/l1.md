Todo empieza con un script de 50 líneas que lee un CSV, calcula y escribe un Excel. Funciona. Tres meses después tiene 1.500 líneas: lee de dos fuentes, tiene casos especiales para clientes empresariales, escribe en una base de datos, manda correos. Cambiar una regla de descuento obliga a leerlo entero, y nadie se atreve a tocarlo. ¿Qué pasó?

## Los síntomas

| Síntoma | Causa |
|---|---|
| Para probar una regla de negocio necesitas archivos reales | La regla está **mezclada** con la lectura |
| Cambiar de CSV a base de datos implica tocar cálculos | Los cálculos **conocen** el formato de los datos |
| Una corrección en el reporte rompe la facturación | Todo depende de todo |
| Nadie sabe dónde está "la regla del IVA" | Está repetida en tres lugares |

## Las capas

La solución clásica es separar el programa por **responsabilidades**, en capas:

El **dominio** es lo que sabe un experto en facturación sin saber programar: qué es un plan, cómo se calcula el excedente de minutos, cuándo aplica el descuento. Son funciones y clases de Python **puras**: no leen archivos, no imprimen, no conocen Pandas ni SQL.
:::
:::paso Aplicación: los casos de uso
"Conciliar el periodo", "cargar el CDR del día", "cambiar el plan de un cliente". Coordinan: piden datos, usan el dominio y entregan resultados. No saben **de dónde** vienen los datos: solo que alguien se los da.
:::
:::paso Infraestructura: el mundo exterior
Leer el CSV en latin-1, consultar PostgreSQL, llamar la API del CRM, escribir el Excel. Aquí viven los detalles técnicos que cambian con el tiempo.
:::
:::paso Interfaz: quién lo usa
La CLI de Typer, un notebook, una tarea programada. Delgada: convierte lo que pide el usuario en una llamada a un caso de uso.
:::
:::

## La regla de las dependencias

La idea más importante del módulo:

:::consejo Las dependencias apuntan hacia adentro
El dominio no importa nada de las capas externas. La aplicación importa el dominio. La infraestructura implementa lo que la aplicación necesita. Nunca al revés: si `dominio.py` tiene `import pandas` o `import sqlite3`, la regla se rompió.
:::

¿Por qué importa? Porque lo de adentro es lo que **menos cambia** y lo que **más vale**. La regla del IVA es la misma si los datos vienen de un CSV o de Oracle. Si cambias de CSV a Oracle, solo cambia la infraestructura.

```pyrun
from dataclasses import dataclass


@dataclass(frozen=True)
class Plan:
    plan_id: str
    minutos_incluidos: int
    tarifa_minuto: int


def valor_voz(minutos: int, plan: Plan) -> int:
    """Regla de negocio pura: sin archivos, sin prints, sin Pandas."""
    if plan.minutos_incluidos == -1:
        return 0
    return max(0, minutos - plan.minutos_incluidos) * plan.tarifa_minuto


hog30 = Plan("HOG30", 300, 120)
ilim = Plan("ILIM", -1, 0)
for minutos, plan in [(342, hog30), (120, hog30), (5000, ilim)]:
    print(f"{plan.plan_id}: {minutos} min → ${valor_voz(minutos, plan):,}")
```

:::capo No todo necesita capas
Un análisis exploratorio de una tarde, un notebook para una reunión, un script que se usará una vez: **no** los separes en capas, sería burocracia. Las capas pagan su costo cuando el programa **vive** (se usa cada mes, lo mantienen varias personas, cambian sus fuentes). Una buena señal para empezar a separar: la segunda vez que copias y pegas una regla, o la primera vez que necesitas probarla.
:::

## Cuestionario

? ¿Qué debe contener la capa de dominio?
- [ ] La lectura de los CSV
- [x] Las reglas de negocio, como funciones y clases puras
- [ ] La CLI
- [ ] Las consultas SQL
> El dominio es el conocimiento del negocio, independiente de cómo se guardan o muestran los datos.

? `dominio.py` tiene `import sqlite3`. ¿Qué problema hay?
- [ ] Ninguno, sqlite3 viene con Python
- [x] El dominio depende de la infraestructura: las dependencias deberían apuntar hacia adentro
- [ ] sqlite3 es lento
- [ ] Debería ser `import sqlalchemy`
> Si el dominio conoce la base de datos, cambiar de base obliga a tocar las reglas de negocio.

? ¿Cuándo NO vale la pena separar en capas?
- [ ] Nunca: siempre vale la pena
- [x] En análisis exploratorios o scripts de una sola vez
- [ ] Cuando el programa se usa todos los meses
- [ ] Cuando varias personas lo mantienen
> Las capas tienen un costo; se justifican en programas que viven y cambian.
